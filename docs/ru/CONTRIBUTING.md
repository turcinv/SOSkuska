# Участие в разработке SOSkúška

[Čeština](../../CONTRIBUTING.md) · [Slovenčina](../sk/CONTRIBUTING.md)

## Перед началом

Прочитай [README](README.md), [основы Git](GIT_GUIDE.md), [руководство разработчика](DEVELOPMENT.md) и [текущую архитектуру](CURRENT_ARCHITECTURE.md). Дополнительные инструкции для ассистентов-разработчиков находятся в [AGENTS.md](../../AGENTS.md).

Работай в новой ветке от актуального `main`. Одно изменение должно решать одну понятную задачу. Реализованы Dashboard, My Subjects и Question bank; не представляй остальные будущие экраны как готовые функции. Новая база должна оставаться пустой, пока пользователь не добавит свои данные. Используй отдельную базу для разработки через `--data .local-data/dev.sqlite3`.

## Перед отправкой

На macOS с подготовленным окружением:

```sh
.venv-macos/bin/python -m compileall -q soskuska tests
.venv-macos/bin/python -m unittest discover -s tests -v
```

На Windows/Linux используй соответствующий путь к Python своего окружения. При изменении UI, таймера или прокрутки запусти также нативную проверку и вручную проверь затронутое поведение:

```sh
.venv-macos/bin/python soskuska/check_dashboard.py
.venv-macos/bin/python soskuska/check_question_bank.py
.venv-macos/bin/python soskuska/check_review_fixes.py
```

GUI-проверка открывает окно и требует графического сеанса. Для изменения только документации обычно достаточно проверить ссылки, команды и форматирование; запускать весь UI ради неё не нужно.

Проверь `git diff --check` и содержимое коммита. Не добавляй виртуальные окружения, базы, кеш, токены или `.env`. Сохраняй пользовательские данные, стабильность UI и работу без интернета. При существенном изменении обновляй чешскую, словацкую и русскую документацию. AGENTS.md остаётся на английском, интерфейс приложения пока тоже.

## Pull request и сообщения о проблемах

Отправь свою ветку и открой pull request в `main`. Опиши проблему, новое поведение и действительно выполненные проверки, включая ОС, Python и Tk. Добавь снимок экрана, если он помогает оценить изменение UI. Не отмечай невыполненные проверки как успешные; синтетические события не доказывают проверку физического трекпада.

Сообщай об ошибке через шаблон в Issues: шаги воспроизведения, ожидаемое/фактическое поведение, окружение и полный релевантный вывод. Предложение функции должно описывать потребность пользователя и ожидаемое поведение. Не прикладывай частную базу или данные доступа. В Issues и pull request можно писать по-чешски, по-словацки, по-английски или по-русски.
